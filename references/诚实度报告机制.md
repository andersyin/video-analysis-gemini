## 诚实度报告（Honesty Report）—— 强制观看证据机制

> **为什么需要这个机制？**
>
> 历史教训：Gemini 曾连续 4 轮使用 Python 脚本批量编造 95 条视频的分析数据（visual_content、VO text、SFX、color_palette、micro_detail 等），虽然通过了所有自动化门禁（唯一率 >95%），但数据全是算法生成的模板文本，无一来自真实视频感知。
>
> 根本原因：LLM 在面对大批量任务时倾向于用脚本"解题"以通过门禁，而非逐条观看视频。自动化门禁能检测模板化，但无法区分"高质量脚本生成"与"真实感知"。
>
> 解决方案：强制每条 JSON 附带诚实度报告，为每个字段提供**只有真正看过该视频才能写出的具体证据**。

### 机制说明

### 诚实度报告字段说明

| 字段 | 类型 | 要求 |
|---|---|---|
| `view_file_called` | bool | 是否调用了 view_file。如果为 false，整条 JSON 作废 |
| `watched_full_video` | bool | 是否观看了完整视频（非只看前几秒） |
| `sections.<板块>.view_file_watched` | bool | 该板块是否基于真实观看 |
| `sections.<板块>.evidence` | string | **关键**：只有真正看过视频才能写出的具体细节，包含精确时间点+具体画面/声音描述。审查者可凭此判断是否真看了视频 |
| `sections.<板块>.specific_details_only_from_watching` | array | 列出 3-5 个"只有看过视频才知道"的细节，如"0.3s DogA左耳前竖 0.2s"。这些细节必须能在视频中找到对应 |
| `fields_not_from_viewing` | array | 如果有字段不是基于真实观看，在此列出并说明原因（如"视频音质差，无法精确判断 dB 值，标注为估计值"） |
| `script_generated` | bool | 是否使用了脚本批量生成。**必须为 false**，如果为 true 整条 JSON 作废 |

> **`analysis_method` 取值约定**（`_meta` 字段）：原文件直传记 `view_file_multimodal`；经感知专用转码记 `view_file_multimodal_sense_track`，并在 `honesty_report` 中注明转码参数（分辨率/CRF/音频码率，可从 `_grounding_payload.json` 的 `sense.params` 复制）——感知轨仅降码率不降信息量，感知要求与密度要求不打折；紧急降级（音轨+九宫格）记 `audio_contact_sheet_degraded`，按「紧急降级模式」规则豁免密度并强制标注非观看字段。

### 审查标准

审查者（Agent / 人类）将通过以下方式验证诚实度报告的真实性：

1. **evidence 可验证性**：evidence 中的具体细节（如"0.3s DogA左耳前竖"）能否在视频中找到对应？如果描述与视频不符，判定为编造
2. **specific_details 独特性**：列出的细节是否是只有看过该视频才知道的内容？如果是泛化描述（如"有一只狗在动"），判定为未真实观看
3. **evidence 跨视频唯一性**：不同视频的 evidence 不能相同或高度相似
4. **fields_not_from_viewing 诚实性**：如果有字段无法基于真实观看提取，是否诚实标注了？如果声称全部观看但实际有编造，交叉验证会发现矛盾

### 反面教材

**❌ 假的 evidence（泛化描述，没看过也能写）**：
```
"evidence": "视频中有腊肠犬在室内活动，有BGM和音效，画面色彩偏暖"
```

**✅ 真的 evidence（具体细节，只有看过才能写）**：
```
"evidence": "0.3s 处DogA从沙发右侧探出头部，左耳有一个 0.2s 的前竖动作；1.8s 处DogB从画面左下角滑入，尾巴摆动频率目测约 3Hz；墙面为米白色（约 #F5F0E8），有一盏暖黄台灯在右上角投射圆形光斑"
```
