## 分析状态机（State Machine）

每条视频的分析任务有以下 6 个标准状态：

```
[UNPROCESSED] 未处理
      │
      ▼
[PREPROCESSED] 预处理完成（Whisper STT + ffprobe + 切帧图）
      │
      ▼
[FLASH_EXTRACTED] Flash 初拆完成（5 板块 JSON + 诚实度报告）
      │
      ▼
[PRO_AUDITING] Pro 质检中（二维审查卡片 + 对抗探针）
   ├── Score >= 90 ───► [PASS_DELIVERED] 交付 + IP SOP 编译
   └── Score < 90  ───► [PROBE_REPAIRING] Flash 定向 Patch 修补
                              │
                              └──► (返回 PRO_AUDITING，满 3 次 ──► [FAILED_CIRCUIT_BROKEN])
```

**熔断保护**：若 `PROBE_REPAIRING` 循环满 3 次仍未达到 90 分，停止重试，写入 `_failed_<date>.json`，避免消耗 API 配额。

状态文件：`<archive-dir>/<account>/videos/<video-id>/_state.json`

**多轮留痕机制（2026-07-25 起）**：
- 每轮质检结果自动归档 `_pro_review_result_r<N>.json` / `_qa_result_r<N>.json`（N = PROBE_REPAIRING 次数 + 1），主文件始终是当前轮，历史轮永不覆盖
- 阶段A 组包写入 `analysis_md5`；组包间隔内 analysis 被修改（手动 patch 或探针修补）会自动记录 `PROBE_REPAIRING`，熔断计数对两条路径都生效
- ingest 校验 packet md5 与当前 analysis 一致，防止拿旧包审新数据
- `PRO_AUDITING` / `PASS_DELIVERED` 状态追加幂等，重复执行不产生重复 history

## 会话寿命管理（Session Lifetime Management）

> **背景（2026-07-26 第二次死亡复盘）**：同一视频今天死了两次，死因都是会话在 L2→L3 间隙耗尽。L2 是 45 分钟的 `view_file` 大流式调用（重活），L3 阶段A 是秒级脚本（轻活）。会话死在"刚干完最重的活、还没来得及跑轻活"的间隙。
>
> **根因不可根除**（网络/平台不可控），但可以通过四层防御把**死亡半径**缩到零——状态机落盘保证每次死亡损失为零或接近零。

### 四层防御

| 层 | 防御措施 | 死亡半径 |
|---|---|---|
| **1. L2→L3 原子绑定** | 写完 `analysis_<date>.json` → 立即跑 `pro_qa_inspector.py`（秒级脚本，零流式） | **零**——L2 落盘即 L3 组包，无间隙 |
| **2. 会话预算上限** | 每会话最多 3 条 L2 完成；第 4 条之前必须开新会话 | 最多 1 条视频的在途损失 |
| **3. 状态机完整性** | 用脚本替代 Agent 手写 `_state.json`，消除早产标记 | 零——状态真实反映进度 |
| **4. 前检查 + watchdog** | 开工前用 `session_guard.py preflight` 扫卡住的视频，优先推进；自动识别「写完收工遗孤」（analysis 齐 5 板块但状态仍 PREPROCESSED）并直指 finalize-l2 | 零——续跑而非开新坑，遗孤必被下次开工扫描抓到 |

### 🔴 规则 1：L2→L3 原子绑定（最高优先级）

**铁律**：在 `analysis_<date>.json` 写入磁盘后、`pro_qa_inspector.py --emit-review-packet` 执行前的间隙，**禁止**执行以下任何操作：
- ❌ 开始新视频的 L1/L2
- ❌ 任何 `view_file` 调用（包括其他视频的 Pro 抽查）
- ❌ 任何其他需要流式传输的操作

**执行顺序**：
1. L2 感知完成 → 保存 `analysis_<date>.json` 到磁盘
2. **紧接着在同一步调用 `session_guard.py finalize-l2`**（一条命令同进程连跑：验证+密度门禁+标记 FLASH_EXTRACTED+L3 阶段A 组包，间隙物理消失）
3. 禁止在步骤 1-2 之间做任何其他操作，**禁止写完 JSON 就结束回合**（历史事故 c97c5b1f：Agent 落盘后空响应收工，产物成孤儿；2026-07-26 铁头阿彪02 再次复现同一违规）。配合渐进落盘铁律的操作化口径：**写入第 5 个板块的那一回合，finalize-l2 必须出现在同一回合内**——末板块写盘与 finalize-l2 之间不允许隔回合。

> 为什么这条规则最重要：`finalize-l2` 是纯本地脚本（Schema 检查 + 密度门禁 + JSON 组包），**零流式传输、零 API 调用**，执行时间 1-2 秒。只要在 L2 落盘后立即执行，死亡半径就是零——即使会话随后死亡，L3 组包已完成，下次续跑从 `PRO_AUDITING` 开始即可。密度门禁不过时同进程拒绝、状态不动，修复后重跑即可（幂等）。旧两步式（mark-flash-extracted + 手动 emit-review-packet）仍可用，但不再推荐。

### 规则 2：会话预算

| 指标 | 软提醒 | 硬限制 |
|---|---|---|
| 每会话 L2 完成数 | ≥ 2 条时提醒"建议尽快收尾" | ≥ 3 条时强制开新会话 |
| 每会话 `view_file` 调用数 | ≥ 10 次时提醒 | ≥ 15 次时强制开新会话 |

> **为什么是 3 条**：今天死亡发生在第 4 个任务前后——前 3 个任务消耗了足够多的 SSE 传输次数和上下文空间，第 4 个任务的存活率已降至临界。限制在 3 条可以把乘积衰减的"掷骰子次数"控制在安全区间。

**开新会话流程**：
1. 当前视频完成 L2→L3 原子绑定（确保不留间隙）
2. 运行 `session_guard.py preflight` 记录当前进度
3. 开新会话 → `session_guard.py preflight` → 继续推进优先级最高的任务

### 规则 3：状态机完整性

**铁律**：只有以下脚本可以写 `_state.json`：
- `preprocessor.py` — 写 `UNPROCESSED → PREPROCESSED`
- `session_guard.py finalize-l2 / mark-flash-extracted` — 写 `PREPROCESSED → FLASH_EXTRACTED`（验证 analysis JSON 存在 + 5 板块齐全 + 密度门禁后才写；finalize-l2 随后同进程拉起 L3 阶段A）
- `pro_qa_inspector.py` — 写 `FLASH_EXTRACTED → PRO_AUDITING / PROBE_REPAIRING / PASS_DELIVERED / FAILED_CIRCUIT_BROKEN`
- `ip_sop_compiler.py` — 写 `PASS_DELIVERED`（幂等）

**禁止 Agent 手写 `_state.json`**。历史教训：Agent 手写 `_state.json` 出现 `"attempts": 0`（脚本从不写此字段）、25 秒早产 `FLASH_EXTRACTED` 标记（实际 L2 需 10-45 分钟）、抹掉脚本写的 `history` 键等问题——导致死亡现场难以预测。

**篡改检测签名**（`session_guard.py validate-state` 自动检查）：

| 签名 | 含义 | 严重度 |
|---|---|---|
| `_state.json` 含 `attempts` 字段 | 脚本从不写此字段，疑似 Agent 手写 | ⚠️ warn |
| 无 `history` 数组 | 脚本总是写 history，疑似手写或截断 | ⚠️ warn |
| `FLASH_EXTRACTED` 距 `PREPROCESSED` < 60s | L2 需 10-45 分钟，疑似早产标记 | 🔴 critical |
| `FLASH_EXTRACTED` 但无 `analysis_*.json` | 状态与产出不一致 | 🔴 critical |

> 如检测到篡改，应视为状态不可信，需根据实际文件产出重新校准状态（用 `session_guard.py mark-flash-extracted` 重标，脚本幂等不会重复写 history）。

### 规则 4：前检查（开工前必做）

**每次开始新会话或处理新视频前**，先运行前检查：

```bash
python3 scripts/session_guard.py preflight \
  --archive-dir /path/to/archive --account "kat-and-oliver"
```

前检查输出优先行动清单：
- **P0_遗孤**（watchdog，2026-07-26 新增）：analysis 已齐 5 板块但状态仍 `PREPROCESSED`（写完收工/会话死亡遗孤，c97c5b1f + 铁头阿彪02 两次复现的行为违规签名）→ **立即补跑 finalize-l2，禁止重进 L2**（重看会浪费一次 45-70 分钟完整感知）；若 analysis 只有部分板块，则推荐「只补缺失板块」续跑（上下文截断恢复路径，以磁盘为准）
- **P1_紧急**：卡在 L2→L3 间隙的视频（`FLASH_EXTRACTED` 但无 `_pro_review_packet.json`）→ **必须先推进再开新坑**
- **P2**：L3 阶段B 待回收 / 修补待重审
- **P3**：`PREPROCESSED` 待 L2 感知
- **P4**：`UNPROCESSED` 待 L1 预处理

> 前检查的核心原则：**优先推进卡住的任务，不要开新坑**。每次死亡后新会话用前检查找到断点，状态机续跑——这就是为什么两次死亡损失接近零。
